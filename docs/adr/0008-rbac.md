# 0008. RBAC

- Status: Accepted, amended by 0015 (adds `commenter` role)
- Date: 2026-10-26
- Source: round-1 Q12, Q13, Q15

## Context
Projects are shared with a coach or personal recruiter, a spouse, or anyone else the owner picks. The same permission rules must drive
API authorization, frontend visibility and the MCP tool list.

## Decision
- **Fixed project roles**: `owner`, `editor`, `viewer`. Custom roles are out of scope.
- One **instance-level** flag, `isInstanceAdmin`, covers instance settings and user management, and grants nothing inside projects.
- Permissions have the form `resource:action`, e.g. `position:read`, `action:create`, `edge:delete`,
  `document:upload`, `member:invite`, `project:transfer`.
- They are defined once in a shared package (`packages/shared/permissions.ts`) through BetterAuth's
  `createAccessControl`, which provides both the role → permission map and the types.
- Consumers:
  - **API**: every route declares the permissions it requires, and the same declaration is emitted as `x-permissions` in OpenAPI (0009);
  - **Frontend**: fetches the current user's effective permissions for the active project and hides or disables UI;
  - **MCP**: filters tools by `x-permissions` (0010).
- No field-level or row-level rules for now.

## Consequences
- A viewer sees everything in the project, salary included. Whether that is acceptable for a recruiter member is open (round-2 Q4).
- A test matrix (role × endpoint, plus cross-project access) is generated from the spec and run in CI.
- The frontend check is only for usability. The API remains the source of truth.
